⚡ Optimeringstips (MVP)

Reducer Firestore Reads

  • Brug pagination (10-20 profiler ad gangen)
  • Cache profiler lokalt i 5-10 min
  • Brug onSnapshot kun til chat
  • Undgå at loade billeder i grid (brug thumbnails)

Location Updates

  • Opdater kun når bruger flytter 50+ meter
  • Brug background location sparingly
  • Batch location updates (max 1/min)

Billeder

  • Compress før upload (max 1MB)
  • Generer thumbnails med Cloud Function
  • Brug CDN caching (automatisk i Storage)

⚡ Kritiske Optimeringer

1. Implementer Caching Layer

Problem: For mange Firestore reads

Løsning:

  • Redis/Memcached for profil data (5-10 min TTL)
  • AsyncStorage cache på device
  • Reducer API calls med 60-80%

2. Optimer Location Queries

Problem: Geohash queries er dyre

Løsning:

  • Brug Algolia for geo-search (bedre performance)
  • Eller byg custom location service (PostGIS)
  • Pre-compute "nearby users" hver 5-10 min

3. Image Optimization Pipeline

Problem: Store billeder = høje bandwidth costs

Løsning:

  • Auto-generate 3 sizes: thumbnail (50px), medium (300px), full (1080px)
  • Brug WebP format (50% mindre end JPEG)
  • Lazy load billeder i chat
  • Imgix eller Cloudinary CDN (optional)

4. Database Denormalization

Problem: For mange joins/queries

Løsning:

  • Gem ofte-brugt data redundant (displayName i chat messages)
  • Reducer reads, men øg writes lidt
  • Reads koster 3x mere end writes!

📍 Location Architecture

PostGIS Queries (PostgreSQL)

-- Find brugere inden for 5km
SELECT user_id, display_name, photo_url,
       ST_Distance(location, ST_MakePoint($userLng, $userLat)::geography) as distance
FROM users
WHERE ST_DWithin(
  location,
  ST_MakePoint($userLng, $userLat)::geography,
  5000  -- 5km i meters
)
AND user_id != $currentUserId
AND is_active = true
ORDER BY distance
LIMIT 50;

Performance: Med spatial index: ~10-50ms (vs 500-2000ms i Firestore)

💾 Cache Strategy:
  • Cache nearby users i Redis i 2-5 min
  • Invalidér kun hvis bruger flytter 100+ meter
  • Reducer database queries med 90%
